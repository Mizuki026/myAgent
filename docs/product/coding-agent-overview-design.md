# 个人 Coding Agent 总概要设计

版本：v1.0。日期：2026-11-02。状态：已确认的总体设计基线。

## 1. 文档定位与设计原则

本文依据 [总需求文档](coding-agent-requirements.md)，确定整体技术路线、八阶段建设安排、开发测试规范和兼容边界。总需求回答产品做什么，本文回答分阶段采用什么方案、如何验证以及各阶段不做什么；每阶段详细设计再确定具体实现。

每阶段统一说明建设目标、技术栈、测试与回归方式、完成标准和不做的内容。本文不规定模块清单、类与函数、HTTP 端点及参数、数据结构、数据表或具体测试脚本，也不提前代替阶段详细设计。

TDD 和回归测试是我们开发 Coding Agent 的工程规范，不据此增加产品运行限制，不修改总需求。产品中每个编码子任务最多三轮实现是已有需求，与开发者进行 TDD 的迭代次数无关。

总体遵循以下原则：

- 在第一阶段已有能力上逐步演进，保留真实结果判定、已有工作保护和变更追踪，不因引入框架而降低这些保障。
- 第二阶段同步建立最小 Web，后续能力逐阶段加入网页；CLI 不作为产品入口，已有 CLI 仅保留其历史实现和自动化验收用途。
- 优先复用社区已有 Harness，采用按阶段开放和验收的方式；允许框架基础依赖提前存在，不将框架自带能力直接视为产品已经完成。
- 每阶段的完成以本机兼容验证、可观察结果和累计回归为依据，不能仅依据框架文档或模型的完成声明。

## 2. 共同技术路线

| 方面 | 选型与用途 |
| --- | --- |
| 运行环境 | Windows 原生，Agent 和开发命令在本机运行，不以 WSL2 或 Docker 为默认执行环境 |
| 后端基础 | 沿用 Python 3.13、uv、Pydantic，管理环境、依赖与输入输出校验 |
| Web 后端 | FastAPI、Uvicorn，承载本机网页所需的任务操作和过程展示 |
| Web 前端 | React、TypeScript、Vite；使用现有 Node.js 24 与 npm |
| 推理模型 | 延续 DeepSeek API，框架接入后验证所选模型及适配方式的兼容性 |
| Harness | Deep Agents SDK，复用其依赖的 LangChain、LangGraph；选择在本机进程中运行的 SDK 方式 |
| 状态持久化 | SQLite；第四阶段结合 Harness 的检查点能力完善任务连续性与恢复 |
| Skill | 个人统一目录中的手写 Skill，采用 `SKILL.md` 格式，复用 Harness 的加载与执行支持 |
| RAG | 本地 Chroma 持久化索引，Sentence Transformers 加载本地多语言 BGE-M3 |
| 后端开发测试 | pytest；Web 后端测试使用 FastAPI 提供的基于 HTTPX 的测试支持 |
| 前端开发测试 | Vitest、React Testing Library；关键浏览器流程使用 Playwright |
| 代码质量 | Python 使用 Ruff；前端执行类型检查、静态检查与构建验证 |
| 版本与协作 | Git 记录变更和交付；第八阶段使用 Git worktree 管理并行代码改动 |

Deep Agents 提供可嵌入自身进程的 Harness，并具备上下文、Skill、规划和子 Agent 等能力。框架选型不等于这些能力已经满足本产品需求，需要按各阶段完成集成与验证。[Deep Agents 官方说明](https://docs.langchain.com/oss/python/deepagents/overview)

依赖采用经过兼容验证的稳定发布版本，并通过锁文件固定；具体版本在相应阶段详细设计与实施时确定。框架或关键依赖升级时，重新验证受影响能力并运行对应回归，不直接跟随最新版本替换运行基线。

## 3. 八阶段建设安排

### 3.1 第一阶段：最小编码闭环，已有实现

| 项目 | 约定 |
| --- | --- |
| 建设目标 | 保留根据用户需求检索、理解和修改 Python 文件中的函数，执行测试与运行验证，并交付修改结果的基础闭环，作为后续演进基线。 |
| 技术栈 | 沿用现有 Python 3.13、uv、Pydantic、DeepSeek 接入、SQLite、文件与进程能力、代码搜索及 Git；已有开发验证使用 pytest 和 Ruff。 |
| 测试与回归方式 | 保留已有行为验收和样例，整理其覆盖范围。当前能否重复通过以实际重新验证为准，不直接沿用历史通过结论；现有离线验证与真实 DeepSeek 效果分别记录。 |
| 完成标准 | 已具备基础实现及配套验证材料；后续开始建设时，先确认这些材料能够作为可重复的行为基线，并明确现有失败、环境限制及覆盖边界。 |
| 不做的内容 | 不为既有实现补造 TDD 过程记录，不重做第一阶段，也不宣称其已覆盖 Web、多语言复杂开发或其他后续需求。 |

第一阶段的历史范围见 [第一阶段设计](coding-agent-mvp-design.md)，已有验证情况见 [第一阶段验证记录](../tests/phase-1-validation.md)。引用这些记录不代表本次文档整理重新执行了产品行为验证。

### 3.2 第二阶段：工具能力与最小 Web

| 项目 | 约定 |
| --- | --- |
| 建设目标 | 完善可供模型调用的完整本机开发工具能力，覆盖代码检索、文件创建与修改、命令执行、版本操作和本地服务管理；同步提供提交任务、查看工具调用过程及结果的最小 Web。 |
| 技术栈 | Python、Pydantic、标准库文件与进程能力、ripgrep、Git；FastAPI、Uvicorn 和 React、TypeScript、Vite。模型驱动暂时沿用现有基础执行流程。 |
| 测试与回归方式 | 从本阶段开始按行为实施 TDD。使用临时项目验证真实文件、命令和版本操作，覆盖 Windows 路径、修改冲突、超时、进程清理及失败反馈。使用 pytest、Vitest、React Testing Library 和 Playwright 建立基础回归，加入 JS/TS 文件与命令场景。 |
| 完成标准 | 用户可通过 Web 提交基础任务并查看真实调用及结果；完整工具集能处理正常与失败情况；JS/TS 基础工具场景和既有 Python 编码闭环回归通过，形成后续阶段可复用的开发验证基线。 |
| 不做的内容 | 不接入新 Harness，不建设复杂任务规划、Skill 或 RAG，不扩展完整的长期任务恢复；不要求本阶段完成 JS/TS 跨文件开发及小型项目新建的全部任务能力。 |

### 3.3 第三阶段：引入 Harness

| 项目 | 约定 |
| --- | --- |
| 建设目标 | 引入社区 Harness，接管模型与工具执行循环，接入任务授权、执行上限和单任务验收条件；继续保留第一阶段已有的实际结果判定与交付保障。 |
| 技术栈 | Deep Agents SDK 及其 LangChain、LangGraph 依赖，适配 DeepSeek API，复用第二阶段的 Windows 本机工具和 Web。 |
| 测试与回归方式 | 先验证所选版本与 DeepSeek、Windows 及现有工具的兼容性，再将第一、二阶段行为纳入新 Harness 回归。通过 TDD 覆盖工具调用、拒绝执行、异常反馈、预算终止以及模型声明与实际结果不一致时的处理。 |
| 完成标准 | 所选 SDK 与模型组合在 Windows 上完成工具调用兼容验证；基础编码闭环能经 Harness 执行，权限、执行上限和验收条件实际生效，累计回归通过。 |
| 不做的内容 | 不将框架附带的规划、Skill、上下文和子 Agent 能力直接作为产品交付；不建设应用层复杂规划或多 Agent 协作，不为实现阶段划分而重新编写整套 Harness。 |

### 3.4 第四阶段：Context Management 与任务恢复

| 项目 | 约定 |
| --- | --- |
| 建设目标 | 完善任务对话连续性、上下文整理、历史查看、暂停、取消和从稳定进度显式恢复；恢复后保留目标、约束、已有成果及累计预算。 |
| 技术栈 | 复用 Deep Agents 的上下文整理能力，结合 SQLite 与 LangGraph 检查点，在已有 Web 中呈现任务控制与恢复情况。 |
| 测试与回归方式 | 通过 TDD 覆盖上下文整理后目标与约束保留、应用重启后的显式恢复、预算不重置、工作区变化识别，以及已执行动作的核对；累计运行前阶段回归。 |
| 完成标准 | 新机制创建的任务能够在保存稳定进度后，经应用重启由用户显式恢复，且工作、证据与预算连续；上下文整理不丢失关键任务依据，任务控制和页面状态一致，累计回归通过。 |
| 不做的内容 | 不建设跨任务的自动长期记忆、异常崩溃或断电恢复，不迁移第一阶段旧任务状态，也不承诺自动重复执行任意中断动作。 |

LangGraph 检查点用于保存任务执行状态；应用所需的显式恢复规则仍需完成集成与验证，不能仅凭配置持久化就视为恢复能力完成。[持久化机制](https://docs.langchain.com/oss/python/langgraph/persistence)

### 3.5 第五阶段：任务规划与完成判定

| 项目 | 约定 |
| --- | --- |
| 建设目标 | 完善自动拆解、子任务依赖、计划调整、进度跟踪与整体完成判定；完整覆盖 Python、JavaScript、TypeScript 跨文件开发和小型项目新建。 |
| 技术栈 | 复用 Deep Agents 的规划能力及已有状态、工具和 Web 技术路线，不另外引入一套并行的 Agent 编排框架。 |
| 测试与回归方式 | 按可观察行为实施 TDD，覆盖任务拆解、依赖顺序、计划调整、每个编码子任务的三轮预算，以及部分完成与整体完成的区别；加入三类语言的完整项目回归，累计验证此前能力。 |
| 完成标准 | 复杂任务可按依赖推进，计划变化可追踪；每个编码子任务预算独立且累计正确，整体结果经过实际验证；三类语言的跨文件任务和小型项目新建通过相应验证与累计回归。 |
| 不做的内容 | 不把第一阶段已有的真实结果判定推迟到本阶段才启用，不引入多 Agent 并行执行或 RAG，不要求一次生成任意规模完整产品。 |

### 3.6 第六阶段：Skill 创建、加载与执行

| 项目 | 约定 |
| --- | --- |
| 建设目标 | 支持用户在个人统一 Skill 库手写创建和维护 Skill，完成校验、按需加载、用户指定与流程执行，并在 Web 中查看使用情况及失败原因。 |
| 技术栈 | 采用 `SKILL.md` 格式和本机个人统一目录，复用 Deep Agents 的 Skill 支持及已有工具执行能力。 |
| 测试与回归方式 | 通过 TDD 覆盖有效与无效 Skill、引用缺失、跨项目复用、用户指定、内容更新和执行失败；根据实际工作结果验证 Skill 是否被使用，而不只检查加载动作；累计运行前阶段回归。 |
| 完成标准 | 手写 Skill 能被识别、校验并在不同项目中按需使用；实际采用内容与结果可追踪，无效或不可用情况明确反馈，累计回归通过。 |
| 不做的内容 | 不实现自然语言自动生成 Skill、任务经验自动提炼、项目独立 Skill 库或语义检索；不将框架读取目录等同于 Skill 已能正确执行。 |

### 3.7 第七阶段：Skill RAG

| 项目 | 约定 |
| --- | --- |
| 建设目标 | 为 Skill 及其明确引用的资料建立语义检索能力，支持候选选择、适用性判断、来源展示和内容更新，并在没有合适结果时如实反馈。 |
| 技术栈 | 本地 Chroma 持久化索引，Sentence Transformers 加载本地多语言 BGE-M3；推理模型继续使用 DeepSeek API。 |
| 测试与回归方式 | 通过 TDD 对索引新增、更新、删除和失败反馈建立确定性回归；另用标注查询集验证真实 Embedding 的匹配、无匹配和误选情况，记录检索效果与本机耗时。检索效果评估与索引行为回归分别记录，累计验证前阶段能力。 |
| 完成标准 | 可依据任务检索并采用适用 Skill，来源和使用原因可查看；内容变化能够反映到后续检索；索引行为回归通过，真实本地模型的检索效果与耗时有可复查记录，达到详细设计约定的阶段标准。 |
| 不做的内容 | 不增加独立知识库，不将项目文档或源码作为独立 RAG 对象；不开发模型训练或微调能力。 |

Chroma 使用本地持久化方式，BGE-M3 通过 Sentence Transformers 在本机加载。具体版本、运行配置、查询集及效果标准在本阶段详细设计中确定。[Chroma 客户端](https://docs.trychroma.com/docs/run-chroma/clients)、[BGE-M3 模型说明](https://huggingface.co/BAAI/bge-m3)

### 3.8 第八阶段：多 Agent 协作

| 项目 | 约定 |
| --- | --- |
| 建设目标 | 提供预置角色的自动调度，按依赖串行或并行工作，隔离代码修改、整合成果并验证整体结果；角色切换不改变同一子任务的累计预算。 |
| 技术栈 | 复用 Deep Agents 子 Agent 能力，结合 Windows 本机并发执行、Git worktree 及已有状态、工具与 Web 能力。 |
| 测试与回归方式 | 通过 TDD 覆盖串行依赖、独立工作并行、修改冲突、子任务失败、整体集成验证和切换角色后预算保留；验证权限不会因委派扩大，并运行前七阶段累计回归。 |
| 完成标准 | 主 Agent 能根据依赖调度预置角色，修改范围与结果可追踪；并行成果能够整合或明确报告冲突，整体成功以集成结果为准，预算和授权规则持续生效，累计回归通过。 |
| 不做的内容 | 不支持用户自定义角色、动态创建角色定义、跨机器协作或多个用户任务的排队系统。 |

## 4. 第二阶段起的 TDD 与回归规范

### 4.1 TDD 的开发方式

- 一次围绕一个可观察行为推进：先写能够暴露缺失行为的失败测试，再实现最小可用改动，通过后将场景保留为回归资产。
- 不采用先批量写完所有测试再统一实现的方式，也不在已有实现完成后补写记录并称其为 TDD。
- 测试关注用户操作与能力结果，不绑定私有方法或内部组织。具体测试入口在相应阶段详细设计中确认后，再开展代码开发。
- 需要整理实现时，在评审中处理，并持续通过已有行为回归。

### 4.2 分层测试与模型使用

| 测试层次 | 技术与关注点 |
| --- | --- |
| 后端行为及集成 | 使用 pytest；通过实际文件、命令、状态和版本操作检验结果，覆盖成功与失败行为 |
| Web 后端 | 使用 FastAPI 基于 HTTPX 的测试支持，验证任务操作、状态与结果反馈 |
| 前端交互 | 使用 Vitest、React Testing Library，围绕用户可见交互验证页面行为 |
| 关键浏览器流程 | 使用 Playwright，贯通任务提交、过程查看、任务控制及结果检查 |
| 模型集成与效果 | 开发回归可使用可控模型响应；真实 DeepSeek 联调和模型效果评估分开组织、分别记录 |
| RAG 效果 | 区分索引行为回归与真实本地 Embedding 的检索效果评估 |

FastAPI 的测试支持基于 HTTPX，React Testing Library 强调从用户使用方式验证交互；这些工具用于我们开发时的验证，不改变 Agent 在用户任务中的模型使用方式。[FastAPI 测试文档](https://fastapi.tiangolo.com/tutorial/testing/)、[React Testing Library](https://testing-library.com/docs/react-testing-library/intro/)、[Playwright](https://playwright.dev/docs/intro)

可控模型响应只替代测试中的外部模型不确定性，不能代替 Agent 完成文件修改、命令执行、状态保存或版本提交。真实模型与本地 Embedding 评估的样本、运行安排及判定标准在阶段详细设计中确定，不在概要中编写具体用例或脚本。

### 4.3 累计回归与阶段交付

- 第二阶段开始前确认第一阶段行为基线，保留现有验收资产；后续每阶段累计保留并验证已经完成的能力。
- 日常 TDD 先运行当前行为所需的检查；代码改动交付前完成所需累计回归和对应质量检查。阶段结束时运行该阶段新增能力与前阶段能力的完整回归。
- 修复缺陷时，先补充能够重现问题的回归测试，再实施修复；不通过删除、跳过测试或放宽判断隐藏失败。
- 已有测试失败时区分运行环境限制和代码缺陷，明确记录原因与影响；不能以历史通过报告代替当前验证，也不能把未验证能力标记为通过。
- 代码改动遵守 [AGENTS.md](../../AGENTS.md)，完成验证并创建对应 Git commit；阶段记录关联相应实现与验证依据。
- 概要设计文档本身的整理不触发产品行为测试。文档整理与阶段代码开发分别处理。

本节只约束我们的开发和交付方式，不要求 Agent 在用户运行任务时只能使用模拟模型，不新增逐步审批要求，也不改变总需求中的任务自主执行规则。

## 5. 兼容与阶段边界

### 5.1 历史实现与任务记录

第三、四阶段保留第一阶段报告和执行证据，不要求旧未完成任务转换到新 Harness 后继续。新机制需要支持其自身任务在应用重启后的显式恢复；跨版本旧状态迁移不纳入本次阶段目标。

第二阶段先建立通用工具及 JS/TS 文件与命令基础回归，第五阶段再完整覆盖 Python、JavaScript、TypeScript 跨文件开发和小型项目新建，避免将基础文本操作视为完整语言能力已经交付。

框架能力的存在与产品能力的完成分别记录。基础依赖可以提前存在，但只有完成应用集成、验证和对应页面能力后，才能在相应阶段宣称交付；不将所有内置能力一次性加入产品范围。

### 5.2 授权与执行范围

权限验证覆盖模型能够触达的全部工具调用路径，包括自定义工具和命令执行。Deep Agents 的内置文件权限不自动覆盖这些路径，不能仅凭框架配置宣称权限能力已经完成。[官方权限说明](https://docs.langchain.com/oss/python/deepagents/permissions)

Windows 原生执行中的路径、进程、超时和权限行为需要实际验证；Git worktree 用于管理代码改动，不代替命令执行权限控制。具体控制方式在阶段详细设计中确定。
